# Transport System — Incremental Development Roadmap

## 1. Purpose

This document defines the order in which the Transport System should be developed using OpenCode.

The system must NOT be generated as one large implementation. Development is divided into small, testable backend phases.

## 2. Technology Stack

- Backend: Python + FastAPI
- ORM: SQLAlchemy
- Database: PostgreSQL
- Database migrations: Alembic
- Authentication: JWT
- Validation: Pydantic
- API documentation: OpenAPI/Swagger generated by FastAPI
- Frontend: Flutter
- Location: GPS-based bus/operator location
- Testing: Pytest
- Environment management: `.env` files locally, environment variables in deployment

## 3. Development Order

### Phase 0 — Project Foundation
Create:
- FastAPI project structure
- Configuration management
- Logging
- Error-handling foundation
- Database connection
- Health-check endpoint
- Alembic setup
- Basic testing setup

Do not implement business features yet.

### Phase 1 — Authentication and Users
Implement:
- User model
- Roles: `COMMUTER`, `OPERATOR`, `MANAGEMENT`
- Registration/login
- Password hashing
- JWT access tokens
- Role-based authorization
- Current-user endpoint

Acceptance:
- Each user can authenticate.
- Protected endpoints reject unauthenticated requests.
- Role restrictions work.

### Phase 2 — Transport Network
Implement:
- Routes
- Stops
- Route stops and their order
- Operators
- Buses
- Operator-to-bus assignment
- Operator route assignment

Acceptance:
- Management can create routes and stops.
- Operators can view/manage their assigned bus and route.
- Commuters can retrieve available routes.

### Phase 3 — Journey Pricing
Implement:
- Route fare configuration
- Fare retrieval
- Operator/management fare management
- Fare validation

Acceptance:
- A commuter selecting a route receives the current fare.

### Phase 4 — Bus Location Tracking
Implement:
- Operator location updates
- Active trip/session
- Latest known bus location
- Location timestamp
- Location freshness rules

Important:
The initial version should not attempt advanced prediction or continuous high-frequency tracking.

The system should store location updates and expose the latest valid location to commuters.

The business requirement says commuters should see bus location information approximately every 20 minutes. The implementation should treat 20 minutes as the commuter-facing update/freshness target, while allowing the operator application to send updates more frequently if required for better ETA accuracy.

### Phase 5 — Commuter Journey Discovery
Implement:
- Select origin/stop
- Select destination/stop
- Find buses serving the route
- Display fare
- Display bus location
- Display last update time
- Estimate arrival time
- Show relevant active buses

Acceptance:
A commuter can choose a journey and understand:
1. Which route to use.
2. Expected fare.
3. Where the relevant bus was last detected.
4. How recently the location was updated.
5. Estimated time to arrival.

### Phase 6 — ETA and Journey Logic
Implement:
- Distance calculations
- ETA calculation
- Route progress
- Basic speed/time estimation
- Handling stale location data

The first ETA implementation should be simple and explainable. Advanced traffic-aware prediction can be added later.

### Phase 7 — Management Analytics
Implement:
- Journey/search records
- Origin/destination statistics
- Route popularity
- Peak periods
- Bus utilization indicators
- Management dashboard API

Management should be able to identify busy routes and destinations without exposing unnecessary commuter personal information.

### Phase 8 — Hardening and Production Readiness
Implement:
- Rate limiting
- Security improvements
- Audit logging
- Monitoring
- Database indexes
- Backup strategy
- Performance testing
- API versioning
- Production deployment

## 4. OpenCode Rule

OpenCode must only implement the phase explicitly requested.

If Phase 1 is requested, it must not automatically build Phase 2, 3, 4, etc.

After every phase:
1. Run tests.
2. Review migrations.
3. Verify API behavior.
4. Fix errors.
5. Update documentation.
6. Commit the completed phase.

## 5. Recommended Commit Pattern

Examples:

```text
feat: initialize transport backend
feat: add authentication and roles
feat: add routes and stops
feat: add bus and operator management
feat: add fare management
feat: add bus location tracking
feat: add commuter route discovery
feat: add ETA calculation
feat: add management analytics
chore: prepare production deployment
```
